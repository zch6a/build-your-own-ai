# Chapter 4 — Inference: fast generation, and choosing what to say

> **Code:** [`byoai/generate.py`](../../byoai/generate.py) (about 170 lines) · **Tests:** [`tests/test_generate.py`](../../tests/test_generate.py) · **Run:** `uv run python chapters/04-inference/run.py`

A trained model gives, for the next position, a probability for every token. Turning that into text
raises two questions every inference engine answers: how to avoid redoing work at each step, and how
to pick a token from the distribution.

## Training code is the wrong tool

Chapter 3's `generate()` calls the training model, which builds an autograd graph it will never use
and — worse — re-runs every layer over the *whole* context to produce one new token. Generating 60
tokens that way does 60 forward passes over a growing sequence.

`Engine` runs the same weights with plain numpy (no graph: `self.p` holds the raw arrays) and adds
the one idea that matters.

## The KV cache

In a causal transformer, position 5's keys and values in every layer depend only on tokens 0–5.
Adding token 50 changes nothing about them. So keep them:

```text
prefill:  forward(prompt)        → logits for the last prompt position; cache K, V of every position
decode:   forward([new token])   → attend from the new position to all cached K, V; append its own
```

```python
cache.k[i] = np.concatenate([cache.k[i], k], axis=1)   # (heads, positions, head_dim)
scores = q @ K.transpose(0, 2, 1) / sqrt(D)             # the new position against all positions
```

The test that matters most here checks that this is *exactly* the same computation: prefill 10
tokens, then decode the rest one by one, and compare the logits at every step with a full forward pass
(to 10⁻⁵). In the demo the cache makes generation about 10× faster — and the gap grows with length,
because the naive way does work proportional to the square of the length, the cached way linear.

The cache has a cost too: memory. Here it is tiny, but for a large model it is
`2 × layers × heads × head_dim × positions` numbers per sequence — gigabytes for long contexts, which is
why serving systems page it in blocks (vLLM), share it between requests with a common prefix, quantize
it, or shrink it with grouped-query attention.

**When the context fills up.** This model learned positions 0–63 only (a table of position vectors),
so it cannot look further back. When the cache reaches 64 positions, the engine rebuilds it from the
most recent 32 tokens and goes on. Models with relative position encodings (RoPE) can slide more
gracefully; none can see beyond its window.

## Sampling: what to say

| strategy | what it does | in the demo |
|---|---|---|
| greedy (`temperature=0`) | always the most likely token | the same story every time (2% distinct) — the most likely path is one path |
| temperature *T* | divide logits by *T* before softmax: *T*<1 sharpens, *T*>1 flattens | 0.5–1.0: fluent and varied; 1.5: the grammar starts to break; 2.5: nonsense |
| top-k | keep only the k most likely tokens | rescues temperature 1.5 (85% fluent) |
| top-p (nucleus) | keep the smallest set whose probabilities sum to p | the same rescue, adapting the set's size to how sure the model is |

"Fluent" in the demo is measurable here because the stories come from a grammar: it is the share of
generated sentences that are real sentences of that grammar. "Distinct" is the share of different
stories among 40.

High temperature makes the long tail of unlikely tokens likely enough to be picked — one bad token and
the sentence is broken. Top-k and top-p cut the tail off *before* sampling, which is why "creative"
settings in real products combine a temperature above 1 with top-p around 0.9: variety among the
plausible tokens, none of the implausible ones.

```python
def sample(logits, temperature=1.0, top_k=None, top_p=None, rng=None):
    if temperature == 0: return argmax(logits)
    logits = logits / temperature
    if top_k:  logits[logits < kth_largest] = -inf
    probs = softmax(logits)
    if top_p:  keep the most likely tokens until their sum reaches p; renormalize
    return rng.choice(len(probs), p=probs)
```

## Streaming

`Engine.stream()` is a generator: it yields each token as soon as it is chosen, which is all "streaming"
means in a chat interface — the server sends each token as it is decoded instead of waiting for the end.
A `stop` set ends the stream on `<|endoftext|>`.

## Where real engines differ

They run on GPUs with fused attention kernels (FlashAttention), keep the cache in pages so thousands of
requests share GPU memory (vLLM's PagedAttention), batch requests continuously as they arrive and
finish, quantize weights to 8 or 4 bits, and use speculative decoding: a small model drafts several
tokens and the large one checks them in a single pass. The cache and the sampling rules are the same as
here.
